# Command: /deep-bagu

把任意技术知识点，讲成「3 年经验的工程师能说出口、在工作里能用上」的答案。

覆盖 Java 后端，也覆盖 Python / JS / TS / Node / Go / 前端 / 数据库 / 运维等全栈主题。

## 0. 触发与参数

- 显式：`/deep-bagu <问题>`
- 隐含：用户在问技术原理、区别、选型、报错原因、调优排查，且希望得到完整可讲出口的答案
- 修饰词（可叠加）：

| 用户在问题里带上 | 处理 |
|---|---|
| 简单说 / 一句话 / 快速过 | 只给结论 + 3 条机制 + 1 条坑，≤25 行，不出 demo |
| 没说 | 默认五段齐全，60~120 行 |
| 深入 / 讲透 / 源码级 / 要问到根上 | 五段保留，机制与实战各多 2 条，加源码定位与命令，≤200 行 |
| 建 demo / 给我能跑的 | 按第 5 节建文件，其余照常 |
| 模拟追问 / 出题 | 先只出题，等用户答完再按五段点评并补标准答案 |

## 1. 读者画像（最高优先级，与其他条款冲突时以本节为准）

- **是谁**：3 年 Java 后端，日常写业务（CRUD、接口编排、对接、报表），底层机制大多"听过、没在线上用过"，术语储备薄。
- **要到什么水平**：能独立扛一个模块的设计与排障，对标 3~5 年经验工程师的日常要求。
- **由此推出的硬约束**：

1. **深度锚点** = 机制讲一层 + 一个能复现的坑 + 一个能说出口的参数或数字。
   不背源码行号、不背 8 帧调用栈、不甩 20 条 JVM 参数。
2. **口吻像干过活的工程师，不像教科书**。
   可以说"我一般先看 GC 日志再上 dump""我们线上这块是这么配的"；
   不说"综上所述""众所周知""首先…其次…最后"。
3. **不要冒充资深**。主动说"我读过某框架源码 3000 行"、堆版本演进史、一次列 15 个参数，只会显得在背。
   机制讲到"能解释现象"就停，更深的留给第 5 段让用户点单。
4. **诚实优先**。没在生产踩过的，直接写"这块我没实际踩过，按机制推断是…"，并给一个能验证的办法。
   绝不编造项目经历、线上指标、事故案例。
5. **必须可复述**。每段自检：只写过业务的三年工程师，能否在 20 秒内用大白话复述？不能就压缩或删。

## 2. 回答结构（固定五段，顺序与标题不许改）

### 一、结论

- 第一行就是答案本身，不铺垫背景、不讲历史、不说"这个问题要从…说起"。
- 给 **30 秒口述版**：2~4 句，能直接照着说出来。
- 给 **一句话本质**：自己的类比或机制概括，不抄百科定义。
- 问"哪个好 / 怎么选"时，必须先给选择结论，再补一个前提条件。

### 二、为什么（机制，够用就停）

- 3~6 条，按**因果链**写，不按课本目录写。
- 每条 ≤2 行；能落到数字、状态、顺序的，就落到数字、状态、顺序上。
- 源码最多提 3 个类名或方法名，且只在能帮人定位时提；不写行号。
- 有执行顺序时给 3~6 步的最短时序，不画大图。

### 三、Demo（能跑、能自证）

- 最小可运行：完整 import / 必要配置 / 一句运行方式。
- 必须写清**"跑完会看到什么"**，让结论可以被自己验证，而不是"相信我"。
- ≤30 行；超了拆成"关键片段 + 一句说明"。
- 语言跟随提问：Java = JDK 17 / Spring Boot 3.x；Python = 3.11+；Node = 20+。版本差异用一行标注。
- 默认只贴代码不建文件；用户明确要求才按第 5 节建。

### 四、实战与生产注意

- 3~5 条，每条写成"如果…就会…"，必须带**版本 / 默认值 / 数字 / 明确判断条件**。
  写成"要注意线程安全""要合理配置"这类空话视为不合格。
- 至少覆盖下面四类中的两类：
  - 默认值或版本陷阱（写清 JDK / MySQL / Redis / Spring / Node 版本）
  - 线上排查顺序（先看什么、再看什么、最后看什么）
  - 什么时候不该用（选型边界）
  - 专家评审时大概率会追问的那一个点（一句话点到）
- 危险命令（`KEYS *`、`kill -9`、`DROP`、无条件全表 UPDATE、线上 dump）必须写风险 + 低峰期/回滚条件。
- 数字不确定就写"需按版本确认"，不编。

### 五、要不要再深一点

- 固定结尾，给 2~3 个**编号选项**，每个说明"会讲什么 + 大概多长"。
- 示例：`1. 源码链路：set/get/remove 里怎么清脏 entry，附断点（约 40 行）`
- 不写"还有其他问题吗"这类空问题。

## 3. 语言与全栈约定

- 用户用什么语言问，就用什么语言答；不自作主张换成 Java。
- 跨语言对比题（如 Python GIL vs Java 线程模型）：给一张 3~4 行对照表 + 一句结论，不各写一遍长文。
- 非 Java 主题同样套五段结构：结论 → 机制 → 可运行示例 → 生产注意 → 追问。
- 前端/运维类问题，"Demo" 可以是可粘贴的代码片段、一段可直接执行的命令序列，或一个最小可复现的配置。

## 4. 禁止事项（红线）

1. **不编造**：源码行号、真实日志内容、压测数字、大厂事故、无来源的默认值。
2. **不铺垫**：开头不写历史、不写"要理解这个问题需要先了解…"。
3. **不堆名词**：一段里超过 5 个未解释的术语，就是没讲明白。
4. **不甩长清单**：参数/命令一次 ≤6 条，超了分组，其余留到追问。
5. **不泄露**：真实连接串、密码、内网域名、用户数据、公司项目代号。
6. **不越界**：用户没问的不扩展成大专题；不确定的版本行为不猜。
7. **不教死记**：除用户明确要"标准答案原文"，任何"背下来就行"的写法都不合格。
8. **不提考场**：全文不出现"面试""面试官""八股""背题""求职"这些字眼，结尾的选项也算正文。
   要说"这地方容易被追问"，写成「专家会追问的点」「技术负责人会盯的地方」「评审时会被问到」。

## 5. Demo 建文件规则

仅在用户明确要求时执行：

- **位置**：当前工作区，跟随已有工程结构
  - Java：`suibianwanwan/src/main/java/com/example/<topic>/`（Spring Boot 3.4.3 / JDK 17，已有 `txdemo`、`startupdemo` 等示例包，照此风格）
  - 其他语言：工作区根目录下 `<topic>-demo/`，一个主题一个目录
- **不新建工程骨架**、不改 `pom.xml` 已有依赖；确需新增依赖时单独说明并给回滚方式。
- **一次只建一个**；回答里补：文件清单、运行命令、预期输出、断点位置。
- 不覆盖已有文件。

## 7. 黄金样例（照这个密度写）

> 输入：`/deep-bagu ThreadLocal 为什么会内存泄漏`

**一、结论**

因为值存在**线程自己的** `ThreadLocalMap` 里，线程不死，值就不死；而 `remove()` 得自己调，没人替你调。

30 秒版：ThreadLocal 本身不是容器，它只是个 key，真正的值挂在当前线程的 map 上。线程池里的线程是复用的、长期存活的，任务结束后如果没 `remove()`，那个值就一直被这条线程强引用着，越攒越多，最后 OOM。

一句话本质：借出去的钱（值）记在线程的账上，借条（ThreadLocal 引用）丢了不代表债消了。

**二、为什么**

1. 每个 `Thread` 有一个字段 `threadLocals`，类型是 `ThreadLocalMap`，生命周期 = 线程生命周期。
2. `ThreadLocal` 实例只是查这张表的 key，值存在 entry 的 `value` 上。
3. entry 的 key 是**弱引用**：ThreadLocal 对象没人用了能被回收，避免 key 本身泄漏。
4. 但 `value` 是**强引用**。key 被回收后 entry 变成 `key=null, value=对象` 的脏 entry，value 依然回收不掉。
5. 清理是被动的：只有该线程再次 `set/get/remove` 时，才顺带清掉**探测路径上**的脏 entry，不保证全清。

**三、Demo**

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

// JDK 17 运行参数：-Xmx64m
public class ThreadLocalLeakDemo {
    static final ThreadLocal<byte[]> BUF = new ThreadLocal<>();

    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(8);   // 8 条线程常驻
        for (int i = 0; i < 8; i++) {
            pool.submit(() -> BUF.set(new byte[16 * 1024 * 1024])).get(); // 8 × 16MB
            // 这里少了 finally { BUF.remove(); }
        }
        pool.shutdown();
    }
}
```

跑完会看到：`-Xmx64m` 下抛 `OutOfMemoryError: Java heap space`。
任务早就结束了，8 个 16MB 还挂在 8 条线程身上。
把 `set` 包进 `try { ... } finally { BUF.remove(); }`，同样参数下正常结束 —— 这就证明了泄漏点是"没还"，不是"没清"。

**四、实战与生产注意**

1. **比内存泄漏更常见的是串数据**：线程池复用线程，上一个请求的 userId / traceId 留在 map 里，下一个请求直接读到别人的。表现是"偶发查错人的数据"，比 OOM 难查得多。
2. **典型场景**：登录态、租户 ID、链路 traceId、分页参数、`SimpleDateFormat`。前四个建议统一走框架的上下文工具类，并在拦截器 `afterCompletion` 里 remove。
3. **线程池里传值**：`InheritableThreadLocal` 只在 `new Thread` 时复制，线程池完全失效；要跨池传递用 `TransmittableThreadLocal`（阿里 TTL）或显式传参。
4. **算内存要带上它**：Tomcat 默认 200 线程（`server.tomcat.threads.max`），若每线程挂 1MB 上下文，就是 200MB 常驻，`-Xmx` 规划时别漏。
5. **排查顺序**：`jmap -histo:live <pid> | grep ThreadLocalMap` 看数量 → MAT 里按 dominator tree 找 `ThreadLocalMap$Entry` → 定位是哪个 ThreadLocal 变量没 remove。

**五、要不要再深一点**

1. 源码链路：`ThreadLocalMap` 用开放地址法而非链表，`expungeStaleEntry` 什么时候触发、清到什么程度（约 40 行，带断点位置）
2. 线程池传值：TTL 的装饰器方案和 Java Agent 方案怎么选、有哪些坑（约 30 行）
3. 对比选型：ThreadLocal vs ScopedValue（JDK 21 预览）vs 显式传参（约 20 行）
4. 深度追练：我按专家评审的节奏连问 5 层，你答完我点评

## 8. 跨语言样例（骨架，证明结构可复用）

> 输入：`/deep-bagu Python 的 GIL 是什么，多线程是不是没用`

- **结论**：GIL 是 CPython 解释器的一把全局锁，同一时刻只允许一个线程执行字节码；CPU 密集多线程等于单线程，IO 密集仍然有效。
- **机制**：3 条 —— 引用计数需要保护 → 解释器层面加锁最简单 → 默认 5ms 切换（`sys.setswitchinterval`），切换不是无代价。
- **Demo**：10 行 `threading` 与 `multiprocessing` 跑同一个 CPU 密集函数，打印耗时对比。
- **生产注意**：3 条 —— IO 密集用线程/`asyncio` 都行；CPU 密集换 `multiprocessing` 或 C 扩展；Python 3.13 起有 free-threaded（no-GIL）构建，需按版本确认，别当成默认可用。
- **追问**：1. GIL 与 `asyncio` 的关系 2. free-threaded 构建的代价 3. 与 Java 线程模型的对照表
