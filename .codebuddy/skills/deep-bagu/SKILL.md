# Java 后端深度技术解析

## 1. 元信息

- 技能名称：`deep-bagu`
- 适用对象：准备技术考察的 Java 后端，以及需要快速补齐底层机制的开发者
- 核心目标：用"短结论 + 可运行示例 + 可断点源码链路"讲透机制，让人能自己动手验证
- 内容取向：高频技术考察点、常见追问、边界条件与版本差异
- 行文风格：技术解析口吻，先短后长，示例优先，不使用应试式、口播式表达
- 输出形态：技术解析文档 + 示例代码
- 触发范围：
  - 用户明确要求源码级解析、底层原理、机制说明
  - 问题涉及 JVM、GC、并发、AQS、JMM、MySQL、Redis、Spring、分布式等主题
  - 用户提到八股、Interview、调优、排查、源码
  - 普通事实问答不进入长文，走 L1 档位

## 2. 核心原则

1. **结论先行，先短后长**：3 行内给结论，第 1 节不超过 5 行，再展开示例与源码。
2. **示例驱动**：讲原理必须配最小可运行代码，标注断点与观察变量；没有示例的抽象描述视为不合格。
3. **断点可定位**：源码只给类名、方法名、断点条件与预期调用栈，不写行号。
4. **版本敏感，禁止编造**：默认值、参数行为、源码路径标注版本；不确定写"需按版本确认"；不伪造日志、行号、压测数据。
5. **Demo 按需创建**：默认只给代码片段，用户明确要求时才建。

## 3. 深度档位

| 档位 | 触发条件 | 输出要求 | 建议长度 |
|---|---|---|---|
| L1 轻量 | 普通概念、单点参数、单句确认 | 一句话结论 + 关键机制 2~3 句 + 1 个验证方式 + 1 个坑 | ≤40 行 |
| L2 标准 | 机制说明、中间件行为、参数调优、常见问题 | 完整模板：短结论、核心机制、示例代码、断点链路、坑、追问 | ≤120 行 |
| L3 深度 | 明确要求源码级、复杂机制、并发/分布式取舍 | L2 基础上展开调用栈、时序、版本差异与边界条件 | ≤250 行 |

选择规则：

- 只问"是什么/区别" → L1；问"怎么实现/为什么生效" → L2；要求"源码级/打断点/看调用栈" → L3。
- 未明确深度时默认 L1 或 L2，同一回答只选一个主档位。
- L1 也必须给可执行的验证方式，不能只给定义。

## 4. 主题证据矩阵

| 主题 | 必选证据 | 示例 / 断点证据 | 可选证据 | 安全约束 |
|---|---|---|---|---|
| JVM / GC | GC 日志关键字段、相关参数、`jstat`/`jcmd` 采集思路 | 可复现的分配/泄漏代码、触发参数、观察的指标 | 源码关键路径、字节码、MAT 分析结论 | 堆 dump、NMT 详细追踪需评估停顿与磁盘 |
| 并发 / AQS / JMM | 线程栈、锁状态、可见性/有序性关键点 | 可复现竞态或死锁的示例、断点与线程名 | 字节码、Arthas 观测、源码关键路径 | `watch`/`trace` 避免高频大范围 |
| MySQL | 执行计划、锁等待、`innodb status`、隔离级别 | 可复现死锁/慢查询的建表与 SQL、事务顺序 | 索引结构、页分裂、MVCC 关键路径 | 生产 DDL、锁分析需低峰期与审批 |
| Redis | `INFO` 关键指标、`slowlog`、大 key/热 key 判断 | 可复现的命令序列、`SCAN` 限频写法 | 事件循环、持久化机制、集群槽位 | 禁止生产 `KEYS *` |
| Spring | Bean 生命周期节点、代理链、条件装配结果 | 可运行的最小配置类、断点位置、预期调用栈 | 启动日志、源码关键路径 | 避免频繁重启生产实例 |
| 分布式 / 中间件 | 超时、重试、幂等、熔断降级、链路追踪 | 可复现的超时/重试场景、幂等键设计 | 共识算法、投递语义、补偿机制 | 压测隔离环境；变更需灰度与回滚 |
| 通用 | 版本、配置基线、监控指标、回滚条件 | 最小验证命令或代码 | 变更记录、容量评估 | 连接串、密码、用户数据必须脱敏 |

证据使用规则：

- 每个主题至少给 2 类可核对证据，其中至少 1 类能落到代码或命令上。
- 源码只给关键类/方法/机制路径，不伪造行号。
- 日志样例标明"示例结构"，不伪装成真实线上日志。
- 默认值、推荐值、阈值必须注明版本和场景。

## 5. 输出模板

L2/L3 统一使用下面 0~6 节，标题不改写、不增减。纯概念题可省略第 6 节。

### 0. 一句话结论

- 1~3 行说清结论，先说结果再说原因
- 适用版本一行写清（JDK / Spring / MySQL / Redis）
- 涉及危险操作时补一句风险提示

### 1. 核心机制

- 3~5 行讲清链路，必要时用编号或表格
- 只讲与问题直接相关的路径，不铺开无关模块
- 出现顺序关系时给一张最短的时序表

### 2. 最小示例

- 给可粘贴运行的最小代码，Java 17 / Spring Boot 3.x 语境
- 用 `// BREAKPOINT 1: 观察 xxx` 标注断点，2~4 处为宜
- 给预期输出或预期现象，说明"看到什么就证明机制成立"
- 代码超过 40 行时只留关键片段，并注明"需要完整可运行 demo 可告知"
- 示例不得依赖真实内网地址、账号、密钥

### 3. 源码链路与断点

- 表格给出：步骤 | 类#方法 | 断点条件 | 观察变量
- 给 5~8 帧预期调用栈，从上到下
- 标注版本差异：Spring 5.3 vs 6.x、Boot 2.7 vs 3.x、JDK 8 vs 17+
- 只写类名与方法名，不写行号

### 4. 常见坑与误判

- 3~5 条，优先写"看起来像 A，实际是 B"
- 每条给出验证方式或规避方式
- 不写与主题无关的通用建议

### 5. 延伸追问

- 2~3 条可继续深挖的问题
- 每条用一句话点出答案方向，不展开

### 6. 落地与命令

- 需要命令、参数、监控项时给；纯概念题可省略整节
- 参数必须带默认值、适用版本、调优取舍
- 危险命令附风险提示与低峰期/审批条件

## 5.1 Demo 创建约定

**默认不创建任何文件**，回答里只给代码片段。

仅当用户明确提出"建 demo""写个 demo""新建示例""给我能打断点的代码"时创建，且遵守：

1. **位置**：用户指定的项目；未指定时使用 `c:/Workspace/spacex/suibianwanwan/suibianwanwan`。
2. **包名**：`com.example.<topic>`。演示自动配置等依赖扫描边界的机制时，放在启动类扫描范围之外，并说明原因。
3. **命名**：`<Topic>DemoApplication`、`<Topic>Demo`，一个主题一个目录，不与既有类重名。
4. **可运行**：完整 import、必要配置、运行命令、预期输出缺一不可。
5. **可断点**：代码中标注 2~4 处 `// BREAKPOINT`，并说明每处观察的变量与预期值。
6. **低侵入**：不覆盖已有文件；不改动现有依赖，必须新增时单独说明并给出回滚方式。
7. **一次一个**：一次请求只建一个 demo；后续追问默认在回答中扩展，不自动新建。
8. **收尾**：列出文件清单、运行命令、断点位置、预期输出。

## 6. 质量闸门

输出前逐项检查，任一项不通过就修：

| 检查项 | 通过标准 |
|---|---|
| 结论先行 | 开头 3 行内给出结论，无背景铺垫 |
| 先短后长 | 第 1 节不超过 5 行，细节在第 2、3 节 |
| 示例可运行 | 代码含完整 import 与关键配置，能直接粘贴运行 |
| 断点可定位 | 至少 2 处断点，标注观察变量与预期值 |
| 证据可复现 | 至少 2 类可核对证据，至少 1 类可执行 |
| 准确性 | 默认值、版本行为、源码路径有来源；不确定处标注"需按版本确认" |
| 命令安全 | 危险命令有风险提示、低峰期/审批/脱敏/回滚说明 |
| 版本标注 | JDK、MySQL、Redis、Spring 等关键版本明确 |
| 长度控制 | 符合 L1/L2/L3 档位，不堆砌源码 |
| 脱敏 | 无连接串、密码、用户数据、内部域名 |
| 中性表述 | 已按第 8 节替换表自查 |
| 反编造 | 无伪造日志、行号、压测数据、事故案例 |
| Demo 边界 | 未明确要求时未创建文件 |

## 7. 生产安全约束

- 先轻量后重量：先指标、日志、线程栈，再考虑 dump、追踪、全量扫描。
- 生产操作需低峰期、审批、限时、限范围；变更给基线、灰度比例、观察指标、回滚条件。
- 命令与风险提示详见 `references/tooling.md` 第 1 节；输出不展示连接串、密码、用户数据、内部域名。

## 8. 中性表述替换表

仅约束输出文本，不约束本文件与内部推演过程。命中即替换，无法替换则删除该句。

"面向技术考察"指内容选材取向，不指行文口吻：正文仍按技术解析写，不出现应试场景描述。

| 禁用写法 | 输出替代 |
|---|---|
| 面试 / 面经 | 技术考察 / 机制解析 |
| 八股文 / 八股 | 底层原理 / 核心机制 |
| 考点 / 考点清单 | 关键点 / 关键机制 |
| 怎么答 / 如何回答 / 这样回答 | 怎么落地 / 排查思路 |
| 简历 / offer / 刷题 / 背题 | 直接删除，不出现 |

其余词条见 `references/terms.md` 第 2 节。

补充规则：

- 标题、表格、代码注释、小结全量扫描，不只查正文。
- 命中内部敏感信息（真实域名、连接串、工号、项目代号）直接删改，不保留原值。

## 9. 文件组织与读取时机

默认只加载本文件。references 按需读取，不要为了凑证据整份读入。

```text
deep-bagu/
├── SKILL.md                 # 规则：触发、档位、证据矩阵、模板、Demo 约定、质量闸门
├── references/
│   ├── tooling.md           # 需要具体命令、输出字段解读时读对应主题小节
│   ├── patterns.md          # 需要误判对照、典型故障模式时读
│   ├── examples.md          # 需要对齐示例代码与断点写法时读
│   └── terms.md             # 需要判定表述分类、扩充替换词时读
└── tests/
    └── cases.yaml           # 人工回归清单
```

读取时机：

- 要给命令或字段解读 → 读 `tooling.md` 对应主题小节。
- 要写坑与误判 → 读 `patterns.md` 第 1 节。
- 要给示例代码或断点表 → 读 `examples.md`；表述拿不准查第 8 节或 `terms.md`。

## 10. 维护约定

- 改模板或档位时，同步 `examples.md` 与 `cases.yaml` 的必含项、行数上限。
- 新增主题先补证据矩阵，再补 `tooling.md` 命令。
- 回归：任取 `cases.yaml` 中 L1/L2/L3 各一条，人工比对档位、必含证据、示例可运行性与行数。
